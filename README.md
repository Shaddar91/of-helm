# of-helm
Helm charts Argo CD deploys on the cluster: `charts/of-api`, the Flask API, and `charts/of-load`, the stress API. Each chart is seeded here by its Terraform stack (`app-services/of-api`, `app-services/of-load` in the infrastructure repository), which also creates the Argo CD Application reading it from `master`; nothing here is applied by hand.
Each chart renders a Deployment, Service, ServiceAccount, HPA (`autoscaling/v2`), PDB (`policy/v1`, `maxUnavailable: 1`), a TargetGroupBinding into the service's target group on the edge ALB and a SecretProviderClass; of-api adds a `db-migrate` Job, an Argo CD PreSync hook that runs `flask --app app init-db` from the same image before every sync, so the API pods only roll once the schema step has succeeded; of-load ships its levels in a ConfigMap. Probes are on `/healthz`.
Settings come from Secrets Manager, never from values. The SecretProviderClass mounts, through the Secrets Store CSI driver with the AWS provider, one file per setting under `/mnt/secrets`: the app secret named after the release (`<environment>-<application>`, written by the stack) and, for of-api, the database secret the aurora stack writes (`<environment>-aurora-database`: `host`, `port`, `dbname`, `username` and `password` as `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER` and `DB_PASSWORD`). Both apps read the files themselves through `SECRETS_DIR`, in process, so the values sit in no Kubernetes Secret and in no environment variable. The pod's service account reads the secrets by EKS Pod Identity, so no role ARN sits in a chart. `secrets.enabled: false` drops the mount and leaves the settings to `env`.
Values the Application sets: `containerPort`, `targetGroupBinding.targetGroupARN`, `image.repository` (the ECR repository URL), `secrets.db.name` (the region's database secret) and `keda.awsRegion`, so no account id, region or region-bound name sits here, and both regions' Applications read this one chart. `image.tag`, the tag CI pushed, ships as `CHANGEME` in the stack's copy and is set before its first apply; of-launch moves it on each deploy.
Arch pinning: the Application stacks `values.yaml` with `values-amd64.yaml` (x86 nodes) or `values-arm64.yaml` (Graviton nodes, tolerating the `arch=arm64:NoSchedule` taint), the file the stack's `architecture` names.
Render locally: `helm template of-api charts/of-api -f charts/of-api/values-amd64.yaml --set image.repository=<registry>/of-api,image.tag=<tag>,containerPort=8000,targetGroupBinding.targetGroupARN=<arn>`, the same for of-load with `values-arm64.yaml`.
CI (`.github/workflows/ci.yml`) is generated by Terraform (the of-helm GitHub stack), so an edit made to it here is overwritten. On each push and pull request to `master` it runs `helm lint` on every chart, validates the render of every values file with kubeconform against the Kubernetes and CRD schemas, with placeholders for what the Application sets, and runs Snyk IaC on the renders; it deploys nothing.
